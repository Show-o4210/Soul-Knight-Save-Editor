# Android 正式版 V1 开发计划

记录日期：2026-10-01。

状态：**计划已获用户支持，核心实现已进入测试候选阶段，alpha14 体验修正供二测；游戏内验收待继续。** 用户确定的三个核心目标为：完善当前逻辑、优化体验、补全专家模式。本页记录实施方案、阶段顺序和验收标准；计划中的能力不计入已经实现的功能。

## 1. 定位与版本区分

正式版 V1 定位为当前 Android 本地存档助手的首个正式交付里程碑，围绕已支持的角色、物品、武器业务完成规则收口和操作体验。继续采用本地 Root 读写，保留首次个人使用确认。

| 名称 | 含义 | 当前情况／建议 |
| --- | --- | --- |
| 正式版 V1 | 本开发计划的产品里程碑名称 | 尚未开发完成，尚未发布 |
| Android 测试版 | 开发、反馈和验证用途的 APK | 当前为 `2.0.0-alpha14` / versionCode 15，调试签名 |
| Android 正式版本号 | APK、更新记录和 Git 标签使用的版本号 | 建议沿用现有版本线，首次正式版为 `2.0.0`；发布前确定 |
| Python 旧版 | `desktop/` 中的独立历史客户端 | 已有 `v1.0.1` 不代表 Android 正式版 V1 |

“V1”是里程碑代号，不要求把 APK 版本号降为 `1.0.0`。本计划起草时未修改版本配置；用户后续授权实施后已生成 alpha12 测试构建，签名与应用 ID 沿用测试基线。

alpha12 的实际实现与共用 API 见[核心实现档案](core-api-alpha12.md)。正式版 V1 是发布里程碑，功能范围可随后续调查与反馈继续扩展；当前候选不定义为最终交付版本。

开发期间继续使用 alpha 测试版本；功能和体验稳定后进入 beta，完成候选验收后使用 rc，达到本计划正式验收条件再交付正式版。各阶段按实际需要推进，不预设发布日期。

- 应用与下载说明清楚标注测试版／正式版及对应版本号，测试包保留验证范围和已知问题。
- 测试版本在 GitHub 中标记为 Pre-release；正式版本通过验收后使用正式发布标记。
- 测试包、正式包分目录存放，分别记录版本、签名类型、构建结果及校验值；已撤回的 alpha10 继续明确标注，不复用其包名作为新交付文件名。
- 正式签名、密钥保管、应用 ID 与测试包覆盖安装策略在发布准备阶段确定；正式包的构建和安装结果需要单独核验。
- 开发状态记录实际能力；本计划记录目标。文档中的“已实现”和“已验收”分别标注，避免把单个样本有效或编译通过写成全面兼容。

## 2. alpha11 基线（实施前）

以 alpha11 为起点：已有可扩展的存档／角色／物品／武器 Tab、渠道特征搜索与单版本选择、账号绑定、跨页预览、自动写前备份、复读校验、事务恢复和结果弹窗。

角色快速功能包括角色、皮肤、等级至少 7、已有技能条目和已有宠物键。物品已支持 573 个确认条目，其中 231 个数量条目仍逐项 +1000。武器使用 `object2ObtainTime`，处理 416 个确认编号武器及存档已有其他武器获取键。实施前的专家模式只有角色和皮肤逐项选择；物品与武器入口当时为预留。

用户已反馈宠物操作有效，并确认宁神与 `weapon_359` 的直接 +8 试验后均可锻造。alpha11 全量武器操作以及全部分类的游戏内验收尚未完整记录。现有 item／武器目录适配 8.6.0，不能由此承诺所有版本或渠道兼容。

实际能力与验证记录见[开发状态](development-status.md)。

## 3. 核心目标一：完善当前逻辑

### 实现方案

1. **整理业务规则。** 为每项操作明确来源文件、账号关联、版本／结构要求、已知 ID、缺失键处理、数值类型和不可用原因。快速与专家模式共用对应业务引擎和 `SavePlan`，参数和选择范围由界面提供。
2. **统一增量与目标值语义。** 增量按扫描原值累加，目标值输入明确表示覆盖；留空不修改，目标值 0 表示清零。校验按字段类型执行，数量检查非负整数和溢出；没有依据时不编造游戏上限。
3. **保证限定范围的修改。** 角色／宠物沿用已识别键与已确认映射，保留已有镜像核对规则；物品沿用已确认目录与排除项；武器沿用正确获取字段。未知字段和非目标账号的记录保留，缺失整个来源文件时显示不可用原因。
4. **完善能力识别。** 每类功能单独展示是否可用及原因，例如文件缺失、版本未适配、结构不符、重复候选；渠道“可发现”和各功能“可编辑”分别说明。物品与武器继续支持不依赖旧 `game.data` 的路径。
5. **保持写回的一致性。** 将角色、物品、武器的组合修改纳入同一事务；只读版本依据也参与写前漂移检查。写回失败不报告部分成功，保留原件与恢复入口；恢复遇到后续游戏进度时继续拒绝自动覆盖。

### 沿用的具体规则

- 角色等级低于 7 时提升至 7，高于 7 时保留；技能只解锁已有条目。
- 宠物按现有映射处理已有键，`Hide` 继续排除。
- 磁带设为 1，蓝图研究至 `Researched`，设施补入列表，饰品补齐／充能至 100；饰品佩戴、图纸、符文等已有记录保留。
- 数量型物品与特殊整数输入沿用[物品规则](quick-items-alpha06.md)。活动材料、专属碎片、细胞等既有排除项继续有效。
- 武器获取次数统一 +8，特殊武器也增加获取次数，科技／蓝图等其他资格继续由游戏判断；规则见[武器说明](quick-weapons-alpha11.md)。
- `.data.new` 和缺失的 XML 读取开关不补造或修改；沿用已存在读取开关的处理，并清楚说明读取来源的限制。

### 验收标准

同一业务在快速／专家模式中产生一致的数据语义；账号隔离、缺失键、重复操作、数值异常及组合操作有明确结果。编码往返、写前漂移、备份、失败恢复等关键路径验证通过。用户验收覆盖代表性已存在／缺失条目及重启后的持久化，不把一个武器或一项材料的结果扩充为全部通过。

## 4. 核心目标二：优化体验

### 实现方案

1. **收尾快速模式。** 将材料、通用武器进化碎片、种子、兑换券改为四个按类别统一 +1000 按钮；每次点击累加一次，展示待增加量和影响条目数，支持撤销。小鱼干与两种角色试玩券继续独立整数输入。逐项数量操作移入专家模式。
2. **统一页面结构。** 保留可扩展 Tab 注册方式；页面依次展示目标游戏／账号、可用状态、操作内容和待修改摘要。备份维持设置中的独立入口，存档扫描与版本选择维持单独页面。
3. **改善列表与选择。** 专家列表支持中文名称／ID 搜索、分类筛选、选中数量、查看已选和清空选择。中文映射不足时显示内部 ID；角色皮肤编号不伪装成游戏排列顺序。
4. **改善预览。** 先按角色／物品／武器显示影响摘要，再展开单项原值、新值和新增记录。明确当前账号和目标游戏；较长列表按需加载，保持确认操作容易找到。
5. **完善草稿反馈。** 切换 Tab 保留待修改项，跨页预览汇总全部选择。切换游戏／账号或重新扫描会清理草稿，界面提前说明；模式切换时明确该模式参与应用的选择，避免另一模式草稿混入。
6. **完善结果与异常提示。** 保留绿色成功标记和折叠详情；显示成功项、失败原因、备份入口及重新扫描动作。格式或版本不支持时给出对应功能的原因；操作期间防止重复提交，搜索保留进度与取消能力。

### 验收标准

快速模式默认不勾选修改项，用户完成常用操作无需展开大量逐项列表。小屏中各 Tab 和确认入口可达；目标、待修改量、预览和结果容易辨认。界面布局、搜索交互、弹窗与游戏内显示主要由用户验收。

## 5. 核心目标三：补全专家模式

专家模式定义为：为当前支持的每类业务提供逐项选择、原值展示和明确的操作参数。继续使用角色／物品／武器 Tab，与快速模式共用识别、编解码、预览和事务保存能力。

| 模块 | V1 专家模式方案 | 数据边界 |
| --- | --- | --- |
| 角色／皮肤 | 保留逐项解锁，补齐搜索、批量选择与已选摘要 | 已识别角色和皮肤键；不通过反向锁定清除进度 |
| 角色等级 | 按角色选择提升至至少 7 级 | 保留更高等级；自由等级上限需另有依据后设计 |
| 角色技能 | 按已有技能条目选择解锁 | 不补造未知技能、不重新锁定 |
| 宠物 | 按已有宠物逐项选择解锁 | 现有映射范围，继续排除 `Hide` |
| 材料／通用碎片／种子／兑换券 | 按条目设置目标数量或自定义增加量，可对已选项批量操作 | 两种输入方式明确区分；沿用目录、排除项与整数校验 |
| 小鱼干／两种试玩券 | 独立目标数量输入，可留空不修改 | 与快速模式相同的三个已确认 ID |
| 磁带 | 按条目选择获取至 1 | 不开放自由数量输入 |
| 蓝图 | 按条目选择研究至 `Researched` | 不回退已有研究进度 |
| 设施 | 按条目选择补入设施列表 | 不删除已有设施记录 |
| 饰品 | 按饰品选择补齐／充能至 100 | 保留已有佩戴、图纸、符文和未知字段 |
| 武器 | 按名称／ID 搜索，显示获取次数，逐项或对选中项增加 8／自定义非负增量 | 使用 `object2ObtainTime`；缺失已知键按 0，特殊资格由游戏判断；不新增缺失未知 ID |

自定义数量和增量均先进入草稿，预览后一次事务应用。V1 优先完成上述已确认语义；角色自由等级、重新锁定、饰品换装／符文配置和武器次数下调等新语义不默认加入本期范围，需要另外确定规则。

### 验收标准

当前每类快速功能均有对应的专家逐项操作。单项、选择子集和批量选择只影响所选记录；未选项及其他账号保持原值。输入错误能定位到条目，空值、0、累加与目标值的含义清楚。快速与专家草稿不会互相误应用。

## 6. 阶段安排

| 阶段 | 工作 | 阶段完成条件 |
| --- | --- | --- |
| P0：规则与基线收口 | 梳理现有数据规则、可用状态和验收缺口；收集 alpha11 全量武器反馈 | 支持范围和待解决问题有记录，关键业务规则清楚 |
| P1：快速模式收尾 | 实现四类统一 +1000，整理跨页摘要与预览 | 快速模式常用批量流程完成，用户完成代表性验收 |
| P2：专家物品与武器 | 先物品逐项数量与已确认解锁，再武器逐项增量 | 可用范围内的逐项／选中批量操作及共用保存链路完成 |
| P3：专家角色与体验收口 | 补角色等级、技能、宠物逐项操作，整理列表、状态、异常提示 | 三个功能 Tab 的专家能力完整，主要交互问题解决 |
| P4：正式候选与交付 | 候选版核心回归、用户游戏验收、正式构建／签名和文档整理 | 达到正式版验收条件后再发布正式版本 |

每轮围绕一个可独立验收的改动交付测试包和简短验收步骤。必要的共用规则调整随对应阶段处理，不要求先搭建大规模通用框架。发现会影响数据正确性的缺口时优先修复，再继续功能开发。

## 7. 验证分工与正式交付条件

**Agent 负责**与改动直接相关的规则检查、关键自动验证和 APK 构建。重点保留编解码、账号／版本绑定、数值溢出、目标记录保留、备份与事务恢复验证；界面小改动按实际风险选择验证，不逐轮重复整套模拟器测试。相关检查通过后交包；出现具体问题时再扩大排查范围。

**用户负责**简单界面操作、布局与提示是否顺手、游戏内效果，以及代表性条目修改后退出／重进的持久化检查。每个测试包附少量明确步骤，反馈按功能记录通过、失败和未验证。

正式候选阶段集中完成一次必要的核心回归，并收口用户反馈。交付条件为：

- 三个核心目标完成，快速／专家模式有清楚且一致的功能范围。
- 受支持业务的代表性游戏内操作与持久化有验收记录；全量 +1000／+8 的代表性结果已核对。
- 关键读写、备份和恢复链路通过；影响数据正确性的已知问题已解决。
- 支持版本／渠道边界、未验证项和后续计划写入文档；不以“所有版本通用”作为宣传。
- 正式构建、签名、安装／更新策略和版本标记明确，交付文件可核对。

普通界面调整不自动触发完整设备回归；正式交付条件也不要求用户逐项测试所有目录 ID。

## 8. 本期范围与后续档案

本期围绕 Android 当前已支持业务推进。ZIP 导入／整包恢复、新增未调查 `.data`、活动或其他未确认字段、跨账号迁移和 Python 旧版业务迁移列入后续候选，不并入这三项核心目标。Python 旧武器按钮的字段错误继续在文档中标明。

需在对应阶段确定的细节：专家列表的最终排版与批量输入方式、正式签名和测试／正式包安装策略、正式 APK 版本号。这些是后续设计或发布准备事项，不代表当前已经实施。

后续功能实现时在[开发状态](development-status.md)登记实际完成情况，在对应测试版说明记录规则变更、验证结果和待用户验收项；本页按阶段更新计划进度。

## 9. alpha12 阶段推进

P0 的共用来源规则与能力报告、P1 四类统一 +1000、P2 专家物品与武器、P3 专家等级／技能／宠物及分组预览已接入源码。体验优化仍可继续，用户候选验收尚未完成，不把上述阶段登记为正式验收通过。P4 的正式签名、发布和正式游戏验收未启动。具体接口和验证范围见[核心实现档案](core-api-alpha12.md)。

alpha13 已落实固定路径连续刷新、卡片说明、包名折叠、紧凑导航与标题／模式动效。用户已测 alpha12 样本有效，未扩大为全部合格；二测规则见[体验档案](experience-alpha13.md)。alpha14 根据体验反馈修正标题滑动方向并加入彩蛋，见[补充档案](header-easter-egg-alpha14.md)，继续保持测试候选定位。
